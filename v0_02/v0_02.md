# version 0.02 alpha

## overview

v0.02 is the first version with real, running code. It delivers **step 1 of the
build path** from the v0.01 design: *a grid map shown in a window, with a
character that moves cell by cell*. The dialogue brain (dramaturge), combat, and
field-of-view are deliberately out of scope here — they arrive in v0.03 and
later.

## what changed

| Area | What happened |
|---|---|
| **Workspace** | Added a Cargo workspace at the repo root with two crates: `engine` (rules) and `game` (Bevy shell). |
| **`engine` crate** | New library crate. Holds the map, tiles, positions, entities, and movement — all pure logic, no rendering. |
| **`game` crate** | New binary crate. A Bevy app that draws the map and the player, reads WASD/arrow keys, and forwards movement to `engine`. |
| **Dependencies** | Pinned `gametools 0.11` (grid/coordinate backbone) and `bevy 0.20` (rendering/ECS). `rpgx` was evaluated and deferred; `gametools` covers grid + pathfinding + FOV and is actively maintained. |
| **Tests** | Unit tests in the `engine` crate for map construction, bounds/terrain checks, spawning, and movement. |
| **Docs** | This file, plus an expanded `README.md`. |

## architecture

```
┌─────────────────────────────── game (Bevy binary) ───────────────────────────────┐
│  setup: build a World, spawn one sprite per tile + the player, point a camera     │
│  handle_movement: read keys -> engine::World::try_move -> sync the sprite         │
└────────────────────────────────────────────┬─────────────────────────────────────┘
                                             │  depends on
┌─────────────────────────────── engine (library) ─────────────────────────────────┐
│  map::Map        wraps gametools::Grid<TileKind>  (bounds, tiles, stepping)      │
│  position::Position  wraps gametools::Point         (col/row + screen mapping)    │
│  entity::Entity  an id, name, position, and stats (AP/HP via MeteredResource)     │
│  world::World    map + entities; spawn() and try_move() enforce the rules        │
└────────────────────────────────────────────┬─────────────────────────────────────┘
                                             │  depends on
                                    gametools (grid, points, deltas, resources)
```

The core idea is **one-way dependency**: `game` knows about `engine`, but
`engine` knows nothing about Bevy. That is why `engine` can be tested with plain
`cargo test`, and why a learner can understand it without learning an ECS first.

## how it works — a guided tour

Read the files in this order; each one builds on the previous.

### 1. `crates/engine/src/map.rs` — the terrain

A [`Map`](../crates/engine/src/map.rs) wraps `gametools::Grid<TileKind>`. We did
**not** write our own 2D array: `gametools` already provides a validated,
bounds-checked grid, so we lean on it and keep our own code small.

- [`TileKind`](../crates/engine/src/map.rs) is an enum with two variants
  (`Floor`, `Wall`) and an `is_passable` helper. Growing the world later (doors,
  water, …) means adding enum variants, not rewriting the map.
- `Map::new` and `Map::bordered` build a grid. `bordered` puts walls around the
  edge so the movement demo has something to bump into.
- `Map::is_passable(point)` answers "can someone stand here?" — the single
  question the movement code cares about.
- `Map::step(origin, delta)` is one cell of movement, using `gametools`
  *bounded* topology: stepping off the map returns `None` instead of wrapping.

### 2. `crates/engine/src/position.rs` — where things are

A [`Position`](../crates/engine/src/position.rs) wraps a `gametools::Point`,
which is a `(col, row)` pair with `(0, 0)` at the **top-left**. We wrap it in our
own type for type safety and to keep all coordinate conversions in one place.

The subtle part is [`to_world_xy`](../crates/engine/src/position.rs): the map's
`row` grows **downward**, but Bevy's `y` grows **upward**, so we negate the row.
That tiny function is why "up" on screen corresponds to "north" on the map.

### 3. `crates/engine/src/entity.rs` — the things

An [`Entity`](../crates/engine/src/entity.rs) is an id, a name, a position, and
two stats: `action_points` and `hit_points`. Both stats are
[`MeteredResource`](https://docs.rs/gametools/latest/gametools/metered_resource/index.html)s —
bounded counters that clamp instead of overflowing. We model them now (even
though combat arrives later) so movement and combat share one concept of "a
character with finite resources".

### 4. `crates/engine/src/world.rs` — the rules

A [`World`](../crates/engine/src/world.rs) owns a `Map` and a list of entities.
This is where the **rules** live:

- `spawn` refuses duplicate ids and refuses to place an entity on a wall.
- `try_move` refuses three things: an unknown entity, a destination outside the
  map, and a destination that's a wall. Each refusal returns a
  [`WorldError`](../crates/engine/src/world.rs) that says exactly what went
  wrong, and the entity stays put.

Notice the shape of `try_move`: **check everything, then mutate**. That pattern —
validate against the current state, and only change state if all checks pass —
is the whole game. Later systems (combat, dialogue) read and write the same
`World` with the same discipline.

### 5. `crates/game/src/main.rs` — the window

The [`game`](../crates/game/src/main.rs) binary is intentionally thin. In Bevy
terms:

- `setup` runs once: build the `World`, spawn a `Sprite` per tile (colored by
  terrain), spawn a brighter sprite for the player, and point a `Camera2d` at
  the map's center. The world itself is stored as a `Resource` so systems can
  read and mutate it.
- `handle_movement` runs every frame: read the arrow/WASD keys, turn a key into
  a `PointDelta`, call `World::try_move`, and — only if it succeeded — move the
  player's sprite to the new cell.

The key discipline: **the sprite only moves if `engine` said the move was
legal**. The renderer never decides "can I walk here"; it just reflects the
engine's answer.

## how to run

```sh
cargo run -p game    # arrow keys / WASD move; Esc closes
cargo test           # engine unit tests
cargo clippy --all-targets -- -D warnings
cargo doc --no-deps  # browse the API locally
```

## known limitations (deliberate, for now)

- Only one entity, and it's the player. NPCs come with dramaturge in v0.03.
- Movement is one cell per key press; there's no pathfinding, animation, or
  action-point cost yet.
- The map is generated in code. Loading maps from files (e.g. Tiled) is a later
  milestone.
- No field-of-view: you can see the whole map. `gametools::fov` is ready when we
  want it.

## roadmap → v0.03

1. **Integrate `dramaturge`** — add one NPC who "remembers" a fact about the
   player. Completing an action sets the fact, and dialogue options change
   accordingly. This validates the narrative loop from the v0.01 plan.
2. **A minimal dialogue UI** — show NPC text and the player's choices in a Bevy
   panel, feeding `dramaturge`'s runtime.
3. **World-state bridge** — decide how `engine::World` and `dramaturge`'s
   `DialogWorldState` share state, so combat/inventory/dialogue read and write
   one world rather than parallel ones.

Stretch: begin combat (action points and turn order via `gametools::ordering`).
